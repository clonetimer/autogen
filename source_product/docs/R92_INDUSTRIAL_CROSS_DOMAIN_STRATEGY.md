# R92 — autogen 跨领域工业故障诊断：现状、边界与产品路线

**状态：2026-10-25，产品方向冻结建议，研究路线规划；本文件不是 Stable 新增能力证书。**  
**本工作从稳定 `main` 独立开分支，不依赖 R75–R91 的级联 Draft PR 合并。**

## 1. 一句话定义

`autogen` / `phm-design` 的目标应收敛为：

> **根据设备与业务任务约束、合法可观测传感器及带来源的数据，自动提出并执行受资源约束的故障诊断算法候选，在独立验证中比较，最终输出带适用范围、失败/拒答条件和复现凭据的算法制品。**

该“通用”是**任务合同、设计搜索与评价流程通用**，不是“一个训练好的模型对所有设备通用”。

核心研究对象是 *algorithm design / selection*，不是证明某个自组织模糊神经网络始终占优。R83f/R83g 的原生 Basilisk 结果不支持自动宣称自组织算法更强；R86–R87 仅建立了模糊前件优化与规则消融机制。

## 2. 核对后的现有功能边界

### 2.1 真正处于 main 的能力

- `main` 经核验为 `b8f1796d2f8216449e130d04537be00901e2248f`，根 `README.md` 与 `source_product/pyproject.toml` 标记 `phm-design 0.7.0`。
- 现有发行资格**仅在限定的 15 个卫星/Basilisk 仿真域离线诊断条件**内成立；该资格不自动赋予后续任意训练权重。禁止表述为真实飞行、任意工业设备、在线闭环诊断或硬件安全控制已被批准。
- 主干存在图结构组合算法设计、限定域数据处理/模型推理、风险拒答、命令行入口及稳定版本回归功能；这些**不等价于完整工业现场 AutoML 产品**。
- `source_product/README.md` 含大量历史开发说明，与根 README 最新发布口径不同。正式版本范围应以稳定发行决策文件及冻结证书为准；历史文本不能累计成当前工业通用承诺。

### 2.3 明确不属于当前能力

**不得承诺：** 不同工业设备即插即用诊断；已训练万能诊断模型；工业现场 OPC UA/MQTT 安全接入；实时工厂 SCADA/PLC 控制；任意设备 RUL 精确预测；无标签自动得知真实故障类别；机理图自动等于真实物理关系；完整非程序员可操作前端；工业/飞行硬件安全认证；真实机器验证的自组织模糊性能提升。

上述能力可在后续提出独立需求和验证项目，但不能借现有科研成果宣称已经完成。

## 3. 跨工业设备共性：从设备专用算法转成任务驱动算法设计

### 3.1 平台内核：5 个稳定合同

1. **EquipmentCard**：设备类别、单机/部件拓扑、设备与运行段身份、传感器可观测性、工程单位、采样规则、标定依据；部件名与具体传感器名称不应写死在通用设计器中。
2. **TaskSpec**：分类（正常/故障类型）、异常检测（可能只有正常标签）、定位（需要可辨识关系）、退化/RUL（需失效时间与删失定义），明确任务目标及不可达/拒绝条件；不同任务不得冒用同一“准确率”。
3. **DatasetCard**：文件版本/许可、测量/物理仿真/合成来源、角色 TRAIN/CAL/VAL/FINAL、物理实体/试验批次/工况、采样时间、质量与缺失、标签来源、重复轨迹指纹、是否可对外发表。
4. **TrialSpec**：预先注册候选集、观察通道、训练/校准/选择策略、随机种子和 CPU/GPU、内存、模型大小、训练时间、最大试验次数；不得不同算法采用不同数据/不同目标，再宣称“公平”。
5. **ModelCard + EvidenceReceipt**：模型/预处理 SHA、训练与验证来源、性能指标和区间、适用工况、推理输入输出、延迟/资源、异常/拒答、安全边界；研究证据与发布资格严格分开。

先用 Python + JSON/JSONL，必要时由外部适配器提供 Parquet/CSV 等；**不要现在就为了“通用”重构已有数据库、全部后端或 UI**。

### 3.2 推荐的 4 条业务主线

| 设备/场景 | 最先实现的任务 | 传感器/挑战 | 合适的证据来源 |
|---|---|---|---|
| **旋转机械：轴承、风机、电机、齿轮箱** | 离线故障检测、分类、跨工况鲁棒性 | 高频振动、电流、速度、负载；设备 ID 必须隔离 | Paderborn（6 健康/26 损坏、4 工况），CWRU 实测信号 |
| **气动与液压：压缩机、泵** | 多变量异常检测、故障事件解释 | 压力、温度、电流、阀状态；事件/工况与时间泄漏 | MetroPT-3 实际运营压缩机序列，需审核故障事件及设备独立性 |
| **制造过程与机电设备** | 工况分层检测、设备级预警、误报/漏报权衡 | 换型、工况漂移、少量异常标签、时间成本 | 将来审核的多设备产线数据；AI4I 为**合成**教学数据，不是真实硬件证明 |
| **卫星/航天器验证适配器** | ADCS/EPS 等部件或分系统离线诊断、可观测性与物理反事实 | 原生 Basilisk 调用链、传感器真实可用性、物理与故障参数一致 | Basilisk 原生仿真；不得称作实星测量 |

长周期 RUL 是**独立任务轨道**：必须先解决生命周期组、维修/删失、失效定义、剩余寿命不确定性；不能简单把分类器换个输出头就宣称已完成。NASA C-MAPSS 等为物理建模/仿真产生的数据，适合独立算法研究但不是实测机队证据。

### 3.3 标准对齐（不是合规认证）

- `ISO 13379-1:2025` 指导机器状态监测与诊断技术选型：重点是正确选择任务与诊断技术，而非固定“最先进”算法。
- `ISO 17359:2018` 是截至 2026-10 已确认仍为现行版的通用状态监测指南，强调监测计划与诊断流程；`ISO 13381-1:2025` 单独面向预测/剩余寿命过程与要求。应将分类诊断与预测建模拆成不同合同。
- OPC UA 为未来工业接入和语义互操作提供可行方向；**当前暂不接入生产写控制接口**，以后采用单独现场安全评审、优先只读采集与离线缓存。
- NIST 对制造业诊断的数据基础设施可信性、复杂设备-系统层级关系以及实际停机/品质代价均有强调，因此不能只优化离线准确率。

## 4. 平台 / 算法库 / 数据平台的职责

`autogen` 负责：

- 将工业任务解释为**可执行、受约束的候选设计方案**；
- 使用公正的数据划分、候选空间和资源预算训练/比较候选；
- 根据源训练反馈和独立验证选择、拒绝或冻结模型；
- 输出可供其他软件执行的诊断算法制品和评估证据。

`autogen` **不应再重复造轮子**：

- 原始数据管理、故障标签编辑、任务查询/UI、数据库运维应属于上层数据和评估平台。例如已有 AAS 可以通过接口提供清洁数据/任务并接收算法输出，但**目前不宣称两个仓库已经无缝集成**。
- 统计方法、ML、NN、RUL 具体算法实例可由专用算法库（例如 `torch_like`）实现；`autogen` 管理算法候选适配协议和比较，**目前不宣称 `torch_like` 接口已经接通**。
- Basilisk/SatAgentSimulation 为真实物理仿真器或数据来源，不应由 `autogen` 替代为仅 Python 构造的“航天器真实数据”。
- 现场采集、OPC UA/MQTT、SCADA/PLC、安全隔离以及非程序员 GUI 属上游/外围专门模块，先要求清晰接口，不把这些功能交给核心搜索器实现。

### 候选算法的最小统一接口

`fit(source_train, config)` / `predict(observed_batch)` / `score_unlabeled(...)` / `export_model()` / `resource_receipt()`，其中实际方法签名将在 P1 由合同测试锁定。

算法能力必须显式标注：任务类型、数据模态、监督/半监督/无监督、是否支持异常拒答、是否支持异步数据、CPU/GPU、依赖包、数据量下限、运行延迟及 **fit/calibration/threshold** 职责归属；不强制所有候选实现完全相同的后处理。

## 5. 现在应明确冻结的技术决策

1. **通用引擎优先于专用模型优越性**：算法自动设计本身是核心，Gaussian/TSK 自组织模糊仅为可选 arm，不进入默认候选 Top-1。
2. **从最简单有效基线开始**：常数/不报警对照、统计阈值、线性模型、树与提升方法，再逐步到 CNN1D/TCN/GRU/Transformer。禁止只拿弱神经网络与新自组织模型比较。
3. **必须按真正独立物理对象拆分**：同一轴承的多窗口、同一个压缩机的不同时间片、同一 Basilisk 真值种子/配对反事实，不能错算多个独立设备。
4. **TRAIN 内的优化不算独立证明**：VAL/TEST/FINAL 的职责严格分离，验证后修改模型需新的事先定义实验，不能继续用同一“盲测”反复调参。
5. **没有来源/物理样本支持时拒绝可信结论**：保留 R89 Paderborn 六健康轴承的严格准入限制；R90 单工况实验属于单独、弱证据研究，不倒灌升级 R88。
6. **公平计算成本**：按 trial 数、实际训练拟合次数、CPU/GPU/墙钟、峰值内存、部署参数和延迟提供 Pareto 证据。R87 前件梯度步和 ridge 重拟合比冻结前件多，不得写成资源公平。
7. **“跨域”分三级**：A) 同一设备不同工况；B) 同一设备家族不同实体；C) 不同设备类别新任务。只通过 A 不得宣传 C。
8. **非程序员体验分层落地**：先 CLI/JSON 明确定义、导出审计，再构建任务向导 UI；避免每个研究 PR 各自造一套前端。

## 7. PR 治理：解决当前“长链 Draft”风险

截至 2026-10-25，`main` 仍为 R60 发行分支状态，R74 至 R91 中大量研究模块以连续 Draft PR 堆叠。把它们一次性合并将混合不同的物理真实性、研究目的、依赖和资格假设。

执行原则：

- R92 从**独立 main 分支**提交，先冻结战略与能力声明，不影响稳定算法调用。
- 后续拆解 R80 TaskSpec + R81 有价值的最小接口和测试；不要以提交数量、PR 数量或分支更新代替产品门禁。
- R86–R91 作为**可选研究插件**保留历史证据和负面研究结果。其真实数据清洗和冻结机制可择优抽取；暂不默认合并全部模糊算法。
- 任何合并需对照现行 0.7.0 的全量回归、Windows/Linux、原有有限稳定资格和产物格式。没有运行过的门禁标为未验证。
- 如果 CI 成功但缺独立设备证据，最多是“工程可执行”，不能升级“跨设备模型已验证”。

## 8. 成功的定义

`autogen` 的目标不应是研发出永远第一的单一模型，而应是：

> 对一个新设备、新传感器组合或新诊断任务，用户能提交明确的数据和约束，让系统自主产生若干可解释的有效候选，按相同协议证明哪些设计更可靠，发现证据不足时明确拒绝，最后交付能复现且适用范围清楚的诊断算法。

这比不断扩充一个可能无泛化优势的自组织网络，更符合工业跨领域应用需求。

**当前 R92 只落地产品能力登记、声明门禁、测试与方向文档；并没有声称 P1–P5 已实现。**
